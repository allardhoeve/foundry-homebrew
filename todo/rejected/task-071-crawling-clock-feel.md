# Task 071: Crawling Clock — die animation and the zero moment

Step 2 of 3. Depends on task 068. Design and rationale live in
`todo/tasks/task-067-crawling-clock-mvp.md`.

## Goal

The part that makes it worth building. The die tumbles on every screen and lands on the
rolled number, the counter ticks down, and hitting 0 is an event: the widget changes
state and a sound plays. The public chat line at 0 already exists from task 068.

This is also where the panel stops being ugly: the design pass on
`crawling-clock.css` belongs here.

## Background

You cannot synchronise animation frames across clients and you do not need to. Everyone
animates locally off the same payload, which arrives within tens of milliseconds on a
LAN. The animation is a pure function of `(rolled, seed)`, so the same payload produces
the same tumble everywhere.

The public chat line at zero was built in task 068 because it is one line and it is what
reaches someone not looking at the widget. What is missing is everything the people who
*are* looking at it should see.

## Changes

### Modified: `module/styles/crawling-clock.css`

- The design pass on the whole panel. Task 068 left it deliberately plain; follow
  `docs/ui-design-guide.md` and the conventions in `module/styles/scarlet-minotaur.css`.
- Die face cycling and the landing state.
- `.crawling-clock--low` at value ≤ 6 for a tension glow.
- `.crawling-clock--stirs` for the zero state: a distinct panel treatment with a pulse or
  glow, and a prominent GM `Reset`.
- Keep every state at the **same fixed height** established in task 068. ApplicationV2
  does not resize itself, and a jumping panel ruins the effect anyway.

### Modified: `module/src/crawling-clock.js`

**Payload**: add `seed`, a random integer generated by the roller, so every client derives
the same face sequence and the die tumbles identically everywhere. Without it each client
invents its own tumble and the dice land on the same number by different routes. Optional
polish; if nobody at your table can see anyone else's screen, drop it and derive the
sequence from `rolled` instead.

**Die animation** in the socket handler's display half:
- Cycle the die face for roughly 800ms, then land on `rolled`. Drive the sequence from
  `seed`.
- Then tick the counter down from the number the widget last painted to the new value.
- If a new payload arrives mid-animation, snap the current one to its end and start the
  new one. No queue.
- A client whose widget is closed, or that opens later, paints the final number with no
  animation.

**Zero moment**, when the new value is 0:
- Every client renders `.crawling-clock--stirs` and the roll button is disabled.
- Every client plays a sound.
- The public chat message already goes out from task 068. Leave that code alone; it is
  posted by the active GM only, so there are no duplicates.

**Reset** leaves the zero state and returns to the normal panel.

## Verification

Dev world, GM in one browser and a player in another.

1. Player rolls → the die tumbles on both screens and lands on the same number, and both
   counters tick down to the same value.
2. Roll twice in quick succession → the first animation snaps to its end, the second
   plays, and the final number is correct on both screens.
3. Drive it to 0 → both screens show the stirs state, both play the sound, and still
   exactly **one** public chat message appears.
4. GM Reset → both screens leave the stirs state and show 20.
5. Open the widget fresh while the clock is mid-session → it paints the current number
   with no animation.
6. Roll with one widget closed, then open it → correct number, no stale animation.

## Pitfalls

- Animation lives in CSS classes, not inline styles (CLAUDE.md).
- Do not animate on the local click and again on the payload; the roller would be
  permanently a round trip out of step with the table.
- The `onChange` repaint is the reconcile path and must **not** animate. It snaps.
- Only the active GM posts the zero message, or every connected GM posts one.
- Fixed panel height, or the window resizes when the stirs state renders.
- Sound: respect Foundry's volume handling rather than playing raw audio, and do not
  block on it.

## Acceptance criteria

- [ ] The die animates on every open widget and lands on the same number
- [ ] Rapid rolls resolve to the correct final number with no queue buildup
- [ ] Zero state renders on every client, with a sound
- [ ] Still exactly one public chat line at zero
- [ ] The low glow appears at ≤ 6
- [ ] The panel looks designed rather than plain, and follows `docs/ui-design-guide.md`
- [ ] Reset returns to the normal state everywhere
- [ ] Opening the widget mid-session paints the current number without animating
- [ ] No inline CSS in the JS

## Scope boundaries

- **In scope**: die animation, the counter tick-down, the low and stirs states, the
  sound, the design pass on the stylesheet.
- **Out of scope**: Dice So Nice integration, richer zero-state animation, in-widget UI
  for the die. All follow-up polish.
- **Do not** rebuild the state model to make animation easier. Adding `seed` to the
  payload is the only change the transport needs.
