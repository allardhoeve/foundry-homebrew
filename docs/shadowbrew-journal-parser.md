# ShadowBrew Journal Parser

A Python tool that extracts hex map entries from ShadowBrew-formatted PDFs and generates Foundry VTT JournalEntry and RollTable JSON documents. Supports incremental chapter-based import: each invocation adds a named chapter to a single journal file.

## Location

`tools/journal-import/import_hexmap.py`

## Prerequisites

- [uv](https://docs.astral.sh/uv/) for Python dependency management
- Dependencies are managed locally in `tools/journal-import/` (no global installs)

## Usage

```bash
cd tools/journal-import
uv run python import_hexmap.py <pdf_path> <first_page> <last_page> --chapter NAME --journal PATH [--name NAME]
```

### Arguments

| Argument | Required | Description |
|----------|----------|-------------|
| `pdf_path` | yes | Path to ShadowBrew PDF |
| `first_page` | yes | First PDF page (1-based) |
| `last_page` | yes | Last PDF page (inclusive) |
| `--chapter` | yes | Chapter name for this batch of pages |
| `--journal` | yes | Path to journal JSON (created if missing, appended if exists) |
| `--name` | no | Journal display name (used only on first creation, default "Journal") |

### Example: building a journal incrementally

```bash
# First run — creates the journal with hex key chapter
uv run python import_hexmap.py ~/devel/Ravens.pdf 20 25 \
  --chapter "Hex Key" \
  --journal ../output/ravens.json \
  --name "Revenge of the Ravens"

# Second run — appends dungeon chapter to the same journal
uv run python import_hexmap.py ~/devel/Ravens.pdf 28 37 \
  --chapter "Mossmoor Ruins" \
  --journal ../output/ravens.json

# Re-running replaces the chapter (idempotent)
uv run python import_hexmap.py ~/devel/Ravens.pdf 20 25 \
  --chapter "Hex Key" \
  --journal ../output/ravens.json
```

Output goes to the journal file's parent directory. Roll tables are written as separate `rolltable-*.json` files alongside.

## What it produces

- **Journal JSON** — A Foundry JournalEntry with pages organized by chapter. Each chapter gets a header page (h1 divider) followed by content pages (h2). Pages include:
  - Bold and italic formatting preserved from the PDF
  - Soft hyphens removed (line-wrapped words rejoined)
  - Cross-references between hex entries as `@UUID` links (e.g. "(504)" becomes a clickable link to the 504. Landel page), resolved across all chapters

- **`rolltable-*.json`** — Foundry RollTable documents for each encounter table found (e.g. "People You Meet in Bark", "Arena Challenger")

## Chapter system

### How chapters work

- Each chapter's pages are tagged with `flags.shadowbrew.chapter` metadata
- The journal tracks chapter order in `flags.shadowbrew.chapters`
- Sort values group chapters: chapter N occupies sort range `(N+1)*1000000` to `(N+2)*1000000-1`
- Re-running a chapter replaces its pages while preserving all other chapters

### Deterministic IDs

Page IDs are deterministic (`sha256(chapter + ":" + page_name)`), so:
- Re-running a chapter produces the same IDs, keeping `@UUID` links from other chapters valid
- The journal ID is deterministic from the journal name

### Cross-chapter references

Parenthesised 3-4 digit numbers like `(504)` are emitted as `@hex[NNN]` placeholders during extraction. After all chapters are assembled, a resolution pass converts these to `@UUID[.page_id]{NNN. Name}` links. Unmatched numbers revert to plain `(NNN)`.

## How it works

### Extraction

Uses pdfminer's layout analysis (`LTTextBox`) to group PDF characters into logical text blocks. Each block is classified by x-range containment:

- **LEFT** — fits entirely left of the page midpoint (210pt)
- **RIGHT** — fits entirely right of the midpoint
- **FULL** — spans the midpoint

This is a geometric fact about each text box, not a heuristic.

### Table group extraction

Tables are detected and extracted **before** column ordering. A table consists of:

1. A die header (e.g. "d6 Opponent")
2. Numbered row blocks below it on the same page

This is necessary because die headers are often physically narrow (LEFT) while table rows span full width (FULL). If we ordered first, the band-based column ordering would separate them.

Table naming priority:
1. A "PEOPLE YOU MEET IN ..." banner above the die header
2. A bold label above the die header (e.g. "Arena Challenger")
3. The nearest hex entry title above on the same page + " Table"

### Ordering

After table extraction, remaining blocks are ordered per page using horizontal bands:
- Full-width blocks define band boundaries
- Within each band: left column top→bottom, then right column top→bottom

### Roll number merging

pdfminer sometimes splits a table roll number ("1", "2") into a tiny separate text box. A post-extraction step merges these with their adjacent text blocks before table detection runs.

## ShadowBrew template conventions

The parser relies on these properties of ShadowBrew PDFs (generated by [The Homebrewery](https://homebrewery.naturalcrit.com/)):

| Element | Font | Size | Detection |
|---------|------|------|-----------|
| Hex entry header | Montserrat-Bold | 12pt | `is_header` flag + regex `^\d+\.\s+` |
| Body text | Montserrat-Regular | 10pt | Default |
| Bold inline | Montserrat-Bold | 10pt | `<strong>` tags |
| Italic inline | Montserrat-Italic | 10pt | `<em>` tags |
| Page title | NewRocker-Regular | 40pt | Skipped |
| Page width | — | 420pt | Column midpoint at 210pt |

## Known limitations

- **Hex key entries only** — The parser currently recognises hex entry headers (`\d+\.\s+NAME` at 12pt bold). Dungeon room headers (10pt bold paragraph headings like "V1. Kobold Burrow.") and prose section headings (14pt bold like "HERALDIC SPEECH") require future parsing modes.

- **Table-to-entry association** — When a table sits below two column entries (e.g. "Arena Challenger" below both Gerta's Cave and The Sewer), the parser cannot determine which entry it belongs to. Tables are output as standalone RollTable documents. Post-processing or manual assignment is needed.

- **Full-page entries** — Entries like "504. Landel" that span both columns are classified as FULL. This works correctly but means they don't appear in a left/right column stream.

- **Multi-column tables** — Tables with more than two columns (e.g. "Giant's Bag" with d12/Content/Smell) have their data columns concatenated into a single text result. Foundry's RollTable format only supports one text field per result. These tables are better used as formatted HTML in the journal page; the GM reads them visually and rolls manually.

- **Images** — Embedded images in the PDF are not extracted. Only text content is parsed.
